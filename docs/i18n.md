# Internationalization (i18n)

Riposte Social's social-frontend ships translated UI in five languages:
English (default + fallback), Spanish, French, Chinese (Simplified), German.

The admin-frontend is currently English-only; backend error messages and
email templates are also English-only. Both are deferred to follow-up
phases after the social-frontend's i18n bedded in.

## Architecture

- **Library**: `react-i18next` + `i18next` + `i18next-browser-languagedetector`
  + `i18next-http-backend`. Initialized in
  [social-frontend/src/i18n.js](../social-frontend/src/i18n.js); a
  side-effect import in [main.jsx](../social-frontend/src/main.jsx) wires
  it up before any component renders.
- **Catalog format**: plain JSON, six namespaces per locale, served as
  static assets from `/locales/{lng}/{ns}.json`. Vite copies them
  verbatim from `social-frontend/public/locales/` into the build output.
  The HTTP backend lazy-loads each namespace on first reference.
- **Plurals**: i18next's native CLDR-aware suffixes (`_one`, `_other`).
  See e.g. `feed:postCard.commentCount_one` / `commentCount_other`. New
  languages with additional plural forms (e.g. Polish, Russian) get
  `_few` / `_many` keys when those locales are added.
- **Embedded markup**: `<Trans i18nKey="…" components={…} />`. Used
  sparingly — only when a translated phrase has an inline link or
  emphasis. The catalog value uses placeholder elements like `<sign>` /
  `<bold>` keyed to the `components` prop.
- **Date / time / number formatting**: `Intl.RelativeTimeFormat` and
  `Intl.DateTimeFormat` via [src/utils/formatTime.js](../social-frontend/src/utils/formatTime.js).
  No per-language code paths; CLDR data ships with the runtime.

## Adding a new language

The whole process is a JSON-only PR. No code changes for the catalogs
themselves, only for the language list.

1. **Pick a base BCP-47 code** (`pt`, `ja`, `ar`, …). Region subtags
   like `pt-BR` are stripped to `pt` by i18next's `load: "languageOnly"`
   setting; one catalog covers the whole base language.
2. **Copy the `en/` directory** to `social-frontend/public/locales/<code>/`
   and translate every value. Structure must match en exactly — the
   `npm run check:i18n` gate refuses a build that drops or adds keys.
3. **Register the code** in two places (kept in sync as a deliberate
   pair so backend and frontend can never disagree on what's accepted):
   - `social-frontend/src/i18n.js::SUPPORTED_LOCALES`
   - `src/profile/locale.rs::SUPPORTED_LOCALES`
4. **Add the native name** to
   `social-frontend/src/i18n.js::LOCALE_NATIVE_NAMES`. Use the
   language's own self-name (`日本語`, `Português`, …) so users
   recognize their language without translating "Japanese" / "Portuguese"
   first.
5. **Run `npm run check:i18n`**. Green = ready to merge.

If the new language has plural categories beyond `one` / `other`
(Russian's `few` / `many`, Arabic's `zero` / `two` / `few` / `many`),
add the extra keys to that locale only. The check script keys off the
*reference* catalog (en) for required keys; locale-only additions don't
fail the check.

## Adding new strings

When adding UI copy in a JSX component:

1. Pick the namespace (or add a new one — see below).
2. Add the key to `social-frontend/public/locales/en/<ns>.json`.
3. In the component, `const { t } = useTranslation("<ns>")` and
   `t("path.to.key")`.
4. Add the same key (with translated value) to every non-English
   locale's `<ns>.json`. The check script will fail the build until
   they're all present, so you can't forget.
5. For plurals: add `_one` / `_other` (and any extras the locale needs)
   suffixes; call as `t("path", { count })`.
6. For interpolation: `{{name}}`-style placeholders. React already
   escapes the value before rendering.

### Adding a new namespace

Rare. Current namespaces map roughly to feature surfaces (common, feed,
compose, settings, auth, browse). If you're adding a substantial new
page that doesn't fit any of these:

1. Pick a name and add it to `NAMESPACES` in `social-frontend/src/i18n.js`.
2. Create `social-frontend/public/locales/<lng>/<new-ns>.json` for every
   locale. Empty `{}` is fine to start; the check script accepts an
   empty reference namespace as long as every locale matches.

## How the user's language gets picked

Decision tree on every page load (in
[social-frontend/src/i18n.js](../social-frontend/src/i18n.js) and
[contexts/AuthContext.jsx](../social-frontend/src/contexts/AuthContext.jsx)):

1. If `localStorage.rs_locale_v1` is set and supported, use it.
2. Else if `navigator.language`'s base code is supported, use it.
3. Else fall back to English.

When AuthContext resolves a user with a non-null `users.locale` that
differs from the active i18n language, `i18n.changeLanguage(user.locale)`
fires once (then a ref blocks re-runs for the page-load). Server is
authoritative for the authenticated session: a user's saved locale
follows them across devices.

When the user picks a language via the LanguagePicker:

- Always: `i18n.changeLanguage(...)` + write to localStorage.
- If authenticated: fire-and-forget `PATCH /api/me/locale`. Failure is
  silent; the local switch already worked.

## Out of scope

- **Backend error i18n**. Errors continue to be English; the frontend
  displays them verbatim via `setError(err.message)`. A future phase
  will introduce a structured `error_code` field on `AppError` JSON
  responses, frontend will map codes to translated messages, verbatim
  message remains the fallback.
- **Email template localization**. `src/email.rs` stays English. A
  future phase will refactor to a template engine with per-locale
  templates keyed off `users.locale`.
- **Admin-frontend translation**. Admin UI stays English; admins are a
  small known set.
- **RTL languages**. None of the five launch locales are RTL. When
  adding Arabic / Hebrew, add a `dir` attribute toggle keyed off
  `i18n.dir(lng)` and the `<html>` element, plus a CSS audit for
  logical-property usage.
- **Translating user-generated content** (post bodies, comment bodies,
  album names). These are authored content, not UI chrome. They are
  rendered as-typed.

## Translation provenance (Phase 11f)

The non-English catalogs landed in this phase as a single-pass
translation. They cover the UI surface but have not yet been reviewed by
native speakers. Open a pass-through review per language as a follow-up;
file findings in this repo's issue tracker as `i18n: <lng>` items.
